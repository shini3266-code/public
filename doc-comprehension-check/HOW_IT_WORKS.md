# 문서 이해도 검사자 (doc-comprehension-check) — 동작 설명서

이 문서는 `doc-comprehension-check` 스킬이 **언제 켜지고, 내부에서 어떤 순서로 움직이며, 왜 그렇게 설계됐는지**를 설명합니다. 스킬의 실제 지시문은 같은 폴더의 `SKILL.md`에 있습니다.

---

## 1. 한 줄 요약

문서를 올리고 "내가 제대로 이해했는지 확인해줘"라고 하면, Claude가 **시험관**이 되어 깊은 이해가 필요한 **서술형 문제를 한 문제씩** 내고, 답할 때마다 **문서 근거를 들어 판정과 피드백**을 줍니다.

---

## 2. 스킬 구성

```
doc-comprehension-check/
├── SKILL.md         ← Claude가 따르는 실제 지시문 (이름·설명 + 진행 규칙)
└── HOW_IT_WORKS.md  ← 지금 보고 있는 설명서 (사람이 읽는 용도)
```

`SKILL.md`는 두 부분으로 되어 있습니다.

| 부분 | 역할 |
|---|---|
| 맨 위 `name` / `description` | Claude가 항상 보고 있는 짧은 소개. **이 스킬을 켤지 말지**를 여기로 판단합니다. |
| 본문 | 스킬이 켜졌을 때만 읽는 상세 규칙 (문제 설계, 진행, 피드백 방식) |

---

## 3. 언제 켜지나요? (트리거)

**켜지는 경우**: 문서를 올리면서 이해도 점검을 원할 때. '시험'이라는 단어가 없어도 됩니다.

- "이 문서 이해했는지 확인해줘"
- "내가 제대로 읽었는지 테스트해줘"
- "이 보고서로 문제 내줘" / "퀴즈 내줘" / "시험 봐줘"
- "check my understanding", "quiz me on this"

**켜지지 않는 경우**: 이해도 확인이 아닌 요청

- "이 문서 요약해줘"
- "3장에 나오는 수치가 뭐야?" 같은 단순 질의응답

대상 문서: PDF, Word, 텍스트, 논문, 보고서, 기획서, 교재 챕터 등. 여러 문서를 함께 올려도 됩니다.

## 4. 전체 흐름

```
 문서 업로드 + "이해도 확인해줘"
          │
          ▼
 ① 문서 정독 ──── 문서가 없으면 → "문서를 올려주세요" 요청 후 대기
          │       (아주 긴 문서면 → "전체로 할까요, 특정 장으로 할까요?" 1회 질문)
          ▼
 ② 문제 설계 (보이지 않게 진행)
    · 핵심 논지, 논리 흐름, 숨은 전제, 개념 간 관계, 함의, 한계를 정리
    · 3~6문제를 만들고 문항별 모범 답안 요지를 미리 정해 둠
          │
          ▼
 ③ 시작 안내 (1~2문장) + 문제 1/N 출제
          │
          ▼
 ④ 사용자 답변 ──▶ 피드백(판정·잘한 점·빠진 점·문서 근거) + 다음 문제
          │                          │
          └──────── 반복 ◀───────────┘
          │
          ▼
 ⑤ 마지막 피드백 후 "모든 문제를 마쳤습니다." 로 종료
```

### ① 문서 정독
문제를 만들기 전에 문서를 **끝까지** 읽습니다. 일부만 읽고 문제를 내면 전체 맥락과 어긋난 질문이 나오기 때문입니다. 이 단계에서 정리한 내용은 사용자에게 보여주지 않습니다. 보여주면 답을 알려주는 셈이 되기 때문입니다.

### ② 문제 설계
"어려운 문제"는 **찾기 어려운 세부사항**이 아니라 **진짜 이해해야 답할 수 있는** 문제를 뜻합니다. 숫자, 날짜, 고유명사 암기 문제는 내지 않습니다. 아래 7가지 유형을 섞어서 출제합니다.

| 유형 | 확인하는 것 | 예시 |
|---|---|---|
| 이유 설명 | 결론과 근거의 연결 | "문서가 A 대신 B를 택한 이유를 문서의 논리로 설명해 보세요." |
| 연결 | 떨어진 개념 간 관계 | "앞부분의 X와 뒷부분의 Y는 어떤 관계인가요?" |
| 적용 | 새 상황에 원리 적용 | "이 원칙을 [문서에 없는 상황]에 적용하면?" |
| 가정 변경 | 전제가 결론을 떠받치는 방식 | "[핵심 전제]가 틀리면 결론의 어디가 흔들리나요?" |
| 함의 추론 | 쓰여 있지 않은 귀결 | "이 주장이 맞다면 [관련 영역]엔 어떤 결과가?" |
| 자기 말로 재구성 | 핵심 압축 능력 | "핵심 논지를 비전공자에게 세 문장으로 설명해 보세요." |
| 한계 파악 | 주장의 범위와 조건 | "이 방법이 통하지 않을 조건과 그 근거는?" |

출제 규칙:
- **문서만으로 답할 수 있어야 함**: 배경지식 시험이 되지 않도록
- **질문에 답을 흘리지 않음**
- **한 문제에 하나의 초점**
- **문서 전체를 고르게** 다루되 곁가지보다 중심 논지를 우선
- **뒤로 갈수록 깊어지게** 배치 (여러 부분을 엮는 문제, 적용 문제를 후반에)
- 여러 문서를 올리면 **문서 간 연결 문제**를 1개 이상 포함

### ③ 진행
한 번에 **한 문제만** 냅니다. 다음 문제를 미리 보여주지 않습니다. 시작 안내도 짧게 합니다. 문서 요약 자체가 힌트가 되기 때문입니다.

```
[문서 제목] 이해도 확인을 시작할게요. 총 4문제, 서술형입니다.

**문제 1/4**
문서가 ... 이유를 문서의 논리로 설명해 보세요.
```

### ④ 피드백 형식
답을 받으면 아래 형식으로 피드백하고, 이어서 **바로 다음 문제**를 냅니다. "다음"을 따로 입력하지 않아도 됩니다.

```
**판정:** 충분함 / 부분적 / 부족함

**잘 짚은 점:** 답에서 정확했던 부분
**빠졌거나 어긋난 점:** 놓친 핵심이나 오해한 부분 (구체적으로)
**문서 근거:** 어느 부분(장·절·페이지)에서 무엇을 말하는지

**문제 2/4**
...
```

피드백 원칙:
- **정직한 판정**: 핵심이 빠졌는데 "좋아요!"라고 하면 이해했다고 착각하게 됩니다. 이 스킬이 잡아내려는 게 바로 그 착각입니다.
- **표현보다 의미**: 문서와 다른 말로 설명해도 의미가 맞으면 정답으로 인정합니다. 자기 말로 설명할 수 있다는 건 오히려 이해했다는 증거입니다.
- **근거는 문서에서**: "제 생각엔"이 아니라 "문서 3절에서 ~라고 하므로"처럼 짚어서, 다시 찾아 읽을 수 있게 위치를 알려줍니다.

## 5. 기본 설정과 바꾸는 방법

| 항목 | 기본값 | 바꾸는 예 |
|---|---|---|
| 진행 방식 | 한 문제씩 대화형 | — |
| 문제 유형 | 서술형만 (객관식·O/X·단답형 없음) | — |
| 난이도 | 어려움 | "좀 쉽게 내줘" |
| 문항 수 | 3~6문제 (문서 분량에 맞춤) | "10문제 내줘" |
| 범위 | 문서 전체 | "2장만 집중해서" |
| 마무리 | 문항별 피드백만, 총점 없음 | "끝나고 총평 해줘" |
| 언어 | 사용자가 쓰는 언어 | 영어 문서도 한국어로 진행, 핵심 용어는 원문 병기 |

## 6. 상황별 대응

| 상황 | 스킬의 반응 |
|---|---|
| 답이 너무 짧거나 모호함 | 채점 전에 **한 번만** 짧게 되물음 (두 번 이상은 안 함) |
| "모르겠어요" / 건너뛰기 | "부족함" 판정 + 모범 답안 요지와 문서 근거 제시 후 다음 문제 |
| 힌트 요청 | 답 대신 **다시 볼 위치나 주목할 관계**만 알려주고 재도전 기회 |
| 채점에 이의 제기 | 문서를 재확인. 사용자가 맞으면 인정하고 판정 수정, 아니면 근거를 들어 설명. 반발만으로 판정을 바꾸지 않음 |
| 중간에 그만두기 | 즉시 종료, 종합 평가 없음 |
| 문서가 매우 김 | 중심 논지 위주로 출제. 범위가 애매하면 시작 전 1회 확인 |

## 7. 사용 예시

> **사용자:** (보고서.pdf 업로드) 이거 다 읽었는데 제대로 이해했는지 확인 좀 해줘
>
> **Claude:** 「2026 물류 자동화 전략 보고서」 이해도 확인을 시작할게요. 총 5문제, 서술형입니다.
>
> **문제 1/5**
> 보고서는 창고 자동화를 "전면 도입"이 아닌 "단계적 도입"으로 권고합니다. 보고서의 논리로 그 이유를 설명해 보세요.
>
> **사용자:** 초기 비용이 커서요.
>
> **Claude:** 그렇게 보신 근거를 한 문장만 더 말씀해 주시겠어요?
>
> **사용자:** 비용이 크고 효과가 불확실하니까 작은 데서 먼저 검증하자는 거요.
>
> **Claude:**
> **판정:** 부분적
>
> **잘 짚은 점:** 효과를 먼저 검증한다는 방향은 맞습니다.
> **빠졌거나 어긋난 점:** 보고서가 든 핵심 이유는 비용이 아니라 기존 WMS와의 연동 리스크입니다. ...
> **문서 근거:** 3.2절 "도입 리스크"에서 ...
>
> **문제 2/5**
> ...

## 8. 설치와 사용

- **Claude.ai / Claude 앱**: 패키징된 `doc-comprehension-check.skill` 파일의 **Save skill** 버튼으로 설치하거나, 설정의 스킬 메뉴에서 이 폴더를 업로드합니다.
- **Claude Code**: 이 폴더를 `~/.claude/skills/` (개인용) 또는 프로젝트의 `.claude/skills/` 아래에 복사합니다.

설치 후 문서를 올리고 "이해도 확인해줘"라고 말하면 자동으로 동작합니다.
